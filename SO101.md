## Train

### SmolVLA

Steps ↔ epochs: `steps_per_epoch = total_frames / batch_size`.
For 3434 frames at batch 8 that's ~430 steps/epoch → 4000 steps ≈ 9 epochs.

```bash
lerobot-train \
  --policy.path=lerobot/smolvla_base \
  --dataset.repo_id=khanhnd61/so101-tape_20260804_224429 \
  --rename_map='{"observation.images.front": "observation.images.camera1", "observation.images.wrist": "observation.images.camera2"}' \
  --batch_size=8 \
  --steps=4000 \
  --policy.scheduler_decay_steps=4000 \
  --policy.scheduler_warmup_steps=200 \
  --save_freq=1000 \
  --output_dir=outputs/train/smolvla_so101_tape \
  --job_name=smolvla_so101_tape \
  --policy.device=cuda \
  --wandb.enable=true \
  --policy.repo_id=khanhnd61/smolvla_so101_tape
```

Smoke test (~1 min, just checks the pipeline runs):

```bash
lerobot-train \
  --policy.path=lerobot/smolvla_base \
  --dataset.repo_id=khanhnd61/so101-tape_20260804_224429 \
  --rename_map='{"observation.images.front": "observation.images.camera1", "observation.images.wrist": "observation.images.camera2"}' \
  --batch_size=4 \
  --steps=100 \
  --save_freq=100 \
  --output_dir=outputs/train/smoke \
  --job_name=smoke \
  --policy.device=cuda \
  --wandb.enable=false \
  --policy.push_to_hub=false
```

Notes:

- `--policy.repo_id` + the default `push_to_hub=true` means the final model is uploaded
  to the Hub (public) when training ends. Add `--policy.push_to_hub=false` to keep it local.
- RTX 3060 12GB: batch 8 with the vision encoder frozen (default) should fit. Unfreezing
  (`--policy.freeze_vision_encoder=false --policy.train_expert_only=false`) improves results
  but needs more VRAM -drop to batch 2–4 if it OOMs.

```bash

  --policy.type=act \

  --batch_size=8 --steps=4000 --save_freq=1000 \
  --output_dir=outputs/train/act_so101_tape --job_name=act_so101_tape \
  --policy.device=cuda --policy.push_to_hub=false
```

### INFLECT

IMPACT's perception with a flow-matching action expert instead of the CVAE + L1 head. Same
dataset and schedule, so IMPACT vs INFLECT is an action-model comparison with the perception
held fixed. 61M learnable parameters against IMPACT's 78M — the CVAE style encoder is gone.

```bash
lerobot-train \
  --policy.type=inflect \
  --dataset.repo_id=khanhnd61/so101-tape_20260804_224429 \
  --batch_size=8 --steps=4000 --save_freq=1000 \
  --output_dir=outputs/train/inflect_so101_tape --job_name=inflect_so101_tape \
  --policy.device=cuda --policy.push_to_hub=false
```

Notes:

- **`--policy.num_steps` is an inference knob**, not a training one: a checkpoint trained at
  the default 10 Euler steps can be served at 5 without retraining. That is the deployment
  lever when latency matters — see the policy README for the stall table.
- **No KL term.** The loss is velocity MSE alone (`flow_loss`), so a run log with a single
  loss component is correct, not a misconfiguration.
- The single-task caveat below applies here too, and more sharply: flow matching exists to
  model a multimodal action distribution, and one task from one operator is close to the
  case where it has nothing extra to model.

Upload

```bash
hf upload khanhnd61/inflect_so101_tape \
  outputs/train/inflect_so101_tape/checkpoints/last/pretrained_model
```

Notes:

- **The frozen T5-small tower is not in the checkpoint.** It is fully determined by its Hub
  id (`google-t5/t5-small`) and is re-fetched on load, so `pretrained_model/` holds the 78M
  trainable tensors and not the 113M total.
- **The instruction comes from the dataset's `single_task` string**, tokenized to 32 tokens
  by the pipeline's `TokenizerProcessorStep`. This dataset has exactly one task, so every
  frame carries the same sentence - which means **this run cannot show that IMPACT uses
  language at all**. It exercises the architecture end to end and gives the CPU port a real
  checkpoint to be validated against; the language claim needs a multi-task dataset whose
  tasks share a scene and differ only by instruction. Do not read a good loss curve here as
  evidence of instruction following.
- `--policy.use_film=false` and `--policy.language_dropout=1.0` are the ablation arms for
  when such a dataset exists.
- Chunk is 50 rather than ACT's 100, so `--policy.n_action_steps` is 50 by default: at
  30 Hz that halves retask latency from 3.33 s to 1.67 s.

Check the server without touching the arm -replays recorded frames at it and
prints the round-trip latency next to the actions:

```bash
lerobot-vla-simd \
  --server_address=127.0.0.1:8080 \
  --replay.repo_id=khanhnd61/so101-tape \
  --replay.steps=10
```

Notes:

- **Camera order is the checkpoint's, not the robot's.** The two backbone passes
  are position-dependent, so a swapped `front`/`wrist` gives plausible, wrong
  actions rather than an error. The server matches them by name (`config.txt`) and
  refuses a session it cannot match, so keep the camera keys named `front`/`wrist`.
- `--task` is accepted but **ACT ignores it** -no language tower, unlike SmolVLA
  above. It is only carried so the same command works against a served VLA.
- `--actions_per_chunk=50` with the default `chunk_size_threshold=0.5` means a new
  chunk is requested once ~25 actions (~0.8 s at 30 fps) remain, which covers the
  ~128 ms inference with room to spare.
- **On a Pi 5 that margin is gone**: ACT is ~943 ms there against 0.83 s of queue, so it
  refills late. Use `--actions_per_chunk=100` (the whole chunk, ~1.67 s) or raise
  `--chunk_size_threshold`. See the rule in the IMPACT section — and note that if the
  queue drains, these two are raised, never lowered.

Check the server without touching the arm — replays recorded frames and prints the
round-trip latency next to the actions:

```bash
lerobot-vla-simd --server_address=127.0.0.1:8080 --policy_type=impact \
  --replay.repo_id=khanhnd61/so101-tape --replay.steps=10
```

Notes:

- **`--policy_type=impact` is required.** The client defaults to `act`, and the server
  refuses a mismatch rather than serving the wrong model — `this server serves impact
  only, the client asked for 'act'`. That rejection is the good outcome; without it a
  50-step chunk would be read as ACT's 100-step one.
- **`--task` matters here, unlike ACT.** The server falls back to the instruction the
  converter recorded in `config.txt`, so omitting it is safe but silent — pass it
  explicitly if you ever serve more than one task from one checkpoint.
- **The instruction is re-encoded only when the string changes**, so a rollout repeating
  one task pays for the T5-small tower and the FiLM head once per episode, not per query.
- **`--actions_per_chunk=25` is a desktop setting. It starves the queue on a Pi.**
  A refill is requested once the queue drops below `actions_per_chunk x chunk_size_threshold`
  actions, i.e. that many / `fps` seconds of motion. The refill has to arrive before the
  queue empties, so:

  ```
  chunk_size_threshold  >  inference_latency x fps / actions_per_chunk
  ```

  With `actions_per_chunk` set to the whole chunk, the right-hand side is exactly
  `latency / (chunk/fps)` — **the stall number**. Stall is not just a benchmark column;
  it is the smallest refill threshold the robot can be run at.

  | | latency | `--actions_per_chunk` | minimum threshold |
  |---|---:|---:|---:|
  | i5 / desktop | 163 ms | 25 | 0.20 — default 0.5 is fine |
  | **Pi 5** | 1286 ms | 25 | **1.54 — impossible** |
  | **Pi 5** | 1286 ms | **50** | **0.77** |

  So on a Pi, request the whole chunk and refill early:

  ```bash
  lerobot-vla-simd --server_address=<pi>:8080 --policy_type=impact \
    --actions_per_chunk=50 --chunk_size_threshold=0.85 --fps=30 \
    --robot.type=so101_follower --robot.port=/dev/ttyACM0 --robot.id=my_awesome_follower_arm \
    --robot.cameras="{front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}, wrist: {type: opencv, index_or_path: 2, width: 640, height: 480, fps: 30}}" \
    --task="Put the tape into the box"
  ```

  **If the queue drains, raise `--chunk_size_threshold` or `--actions_per_chunk` — never
  lower them.** Both appear in the denominator; lowering either makes the starvation worse.
- Camera order is the checkpoint's; the server matches by name and refuses a session it
  cannot match, so keep the keys named `front` / `wrist`.

```bash
  --task="Put the tape into the box" \
  --actions_per_chunk=25 \
  --fps=30
```

Notes:

- **On a Pi 5 the default 10 steps does not hold.** Measured 1529 ms per chunk against
  1.67 s of motion — a stall of 0.918 on a board that drifts 10–15% between sessions, which
  is a coin flip rather than a deployment. At 3 steps it is 1279 ms (stall 0.767), and the
  curve flattens below 3 because what remains is the encoder, which runs once per query
  however many steps the expert takes. On desktop-class silicon 10 steps is comfortable.
- **Whether 3 steps is *accurate* enough is a separate question** these checkpoints cannot
  answer — the step count trades latency against integration accuracy, and deciding it needs
  a success rate, not a latency number. Start at 10 on the bench and step down.
- **`--policy_type=inflect` is required**, as for IMPACT above — the client defaults to
  `act` and the server refuses a mismatch.
- **Serving on a 4-core board?** The server caps its default thread count at the machine's
  cores, but it is a reported parameter, not a guess: check the `threads N` in the load
  line, and set `OMP_NUM_THREADS` explicitly when you care.
- **Queue timing is tighter than IMPACT's, and it decides the step count.** The rule from
  the IMPACT section applies unchanged — `chunk_size_threshold > latency x fps /
  actions_per_chunk`, which at a full chunk is the stall number:

  | Pi 5 | latency | minimum threshold at `--actions_per_chunk=50` |
  |---|---:|---:|
  | 3 Euler steps | 1279 ms | **0.77** — run it at `--chunk_size_threshold=0.85` |
  | 10 Euler steps | 1529 ms | **0.92** — no usable margin, do not deploy |

  This is the same conclusion as the stall table arrived at from the other direction: the
  default 10 steps is a bench setting, not a robot setting. On a desktop both are fine at
  the default 0.5.

- **`--seed` makes a rollout reproducible.** Flow matching draws a starting noise `x_1` per
  query; the server derives it from `seed + query_index`, so two runs of the same episode
  are comparable. Omit it and you still get valid but different trajectories — which is
  correct behaviour for a stochastic policy, and worth knowing before you conclude a run
  was non-deterministic by accident.

### MicroVLA

**One-time**: finetune on the tape dataset. Unlike Octo there is nothing to convert first —
